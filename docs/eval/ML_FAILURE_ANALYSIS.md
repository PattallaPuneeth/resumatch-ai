# ML Matching: Failure Analysis and Fixes (Phase 10)

**Date:** 2026-10-28 (IST) · **Scope:** resume-to-JD match scoring (`ml/pipelines/matching/`, `ml/pipelines/embeddings/`, `ml/pipelines/intake/` skills and ATS) and job suggestions · **Commits:** `5763092`, `160120d`, `b607a1e`, `580d539`, `0f4213a` (plus this report)

Every number below comes from a command that was actually run (section 8 lists them). Scores come from ML only; no LLM or Firecrawl call was made for this work.

---

## 1. Summary

The eval harness reported 97.6% pairwise accuracy on the handwritten set, but it did not run the code users run. On the production path:

1. **Every realistic job description crashed matching.** The worker embedded `title + skills + full JD` as one text, and `generate_embeddings()` refuses anything over 256 tokens. All 8 handwritten JDs are 345–421 tokens, so 8/8 match jobs raised `ValueError` and saved nothing. The k6 match scenario and the e2e smoke both use one-sentence JDs, so nothing caught it.
2. **Every resume got 25 free points.** The analyze page sends only `title` and `rawDescription`, never `requiredSkills`. `analyze_skill_gap([])` returned coverage 1.0, so `0.25 × 100` was added to every match. On the handwritten set the mean weak-pair score was 45.6, above the 45 "medium" cut-off.
3. **The skill map couldn't see most skills.** It had 16 entries: no Java, Kotlin, Spring or Go, and no non-tech skills at all. Accountants, teachers and bankers got near-zero coverage.

After the fixes, measured with the project's own harness (`python -m ml.eval.run`):

| Dataset | Before: production path¹ | Before: old harness | **After (production = harness)** |
| :--- | :---: | :---: | :---: |
| Handwritten, 32 pairs: pairwise / band acc | crashed (8/8 JDs); without the crash 0.880 / 0.625 | 0.976 / 0.875 | **0.982 / 0.938** |
| Kaggle held-out test, 252 pairs: pairwise / band acc | 0.969 / 0.413 | 0.970 / 0.552 | **0.995 / 0.758** |
| Extended, 100 pairs: pairwise / band acc | 0.909 / 0.670 | 0.849 / 0.800 | **0.927 / 0.940** |
| CI fixtures, 5 pairs: pairwise / band acc | 0.750 / 0.600 | 1.000 / 1.000 | **1.000 / 1.000** |
| Handwritten mean score, strong / medium / weak | 84.1 / 56.3 / **45.6** | 83.6 / 55.4 / 21.2 | **88.5 / 57.7 / 22.8** |

¹ "Production path" replays what the worker actually did on the old code: no `requiredSkills` (coverage 1.0), the reranker query built from heading lines, and the semantic score from the first job chunk. The real worker crashed instead of using the first chunk, so for the handwritten set these numbers are better than what users actually got.

"Band acc" is the share of pairs whose score lands in the labeled band (strong ≥ 75, medium 45–75, weak < 45, `ml/eval/metrics.py`).

**Round 2 (2026-10-28, §8):** coverage now reads required vs preferred skills and "X or Y" alternatives, and the skill map gained finance phrasings. This raised Kaggle held-out band accuracy **0.758 → 0.802** (pairwise 0.995 → 0.996) with handwritten, extended and CI unchanged. Two speed ideas were measured and rejected.

| Set | Pairs | Labels | Strength | Weakness |

| `ml/eval/datasets/kaggle_domain` (user-provided) | 629 labeled of 903 | 192 strong / 437 weak (binary) | 301 resumes, 6 non-tech or mixed fields, entry to senior; per-resume tune/test split (377/252) | Labels are **auto-generated by counting required skill groups**, so they reward keyword overlap. | `ml/eval/ci_fixtures` | 5 | 2 / 1 / 2 | Fast CI gate | Too small to detect anything but collapse |

Findings about the data itself:

- **Nothing was versioned.** `test-data/` is gitignored and was never committed, so only the 5-pair CI set was in git. The handwritten and Kaggle sets are now in `ml/eval/datasets/` (`b607a1e`).
- **Leakage.** Earlier calibration work (`ml/eval/calibration.py`) split one 32-pair set 60/40, and the production weights were chosen on the same data that was reported. Here, nothing is fitted on any held-out data: the Kaggle split is per resume (no resume in both), and the handwritten set is never used for fitting.
- **Label noise in the Kaggle set (hand-checked).** R0118 is a working accountant (B.S. Accounting, "Accountant 2010–Present", A/R reporting, reconciliations) labeled *not suitable* for the Accountant job, because the keyword counter didn't map "A/R" to accounts receivable. The model scores it 64.5, and the model is right. R0239 (partner account manager) is labeled *suitable* for Data Analyst on the strength of "Oracle SQL, MS Excel". So on this set, part of the remaining error is the label's, not the model's.
- **Parsing-accuracy benchmark is duplicated.** `docs/eval/parsing_accuracy.md` reports 60 documents, but per-case metrics repeat in identical groups (e.g. cases 01/04/07/10 share every number). They are copies of about 5 sources rendered several ways. Its 100% section accuracy and 78% skill recall describe 5 layouts, not 60.

**Verdict:** the handwritten set is the most trustworthy but small, the Kaggle set adds field diversity with noisy labels, and the extended set mainly tests trivial separation. None of them is a real labeled hiring set. Item 5 in section 6 is the most valuable next step.

## 4. Failures, grouped by cause

### 4.1 Long JDs: semantic query crashed *(fixed)*
- **Evidence:** production query lengths were 345–421 tokens for all 8 handwritten JDs. `generate_embeddings()` raised for 8/8 (measured by calling it on the worker's exact query text).
- **Fix:** `embed_query_text()` (`ml/pipelines/embeddings/embedder.py`) splits a long query into overlapping 254-token windows that fit the model, embeds each, and returns the L2-normalized mean. Stored chunk embeddings stay strict. `semantic.py` uses it. Test: `test_embed_query_text_handles_job_descriptions_longer_than_model_window`.

### 4.2 Empty `requiredSkills`: free coverage *(fixed)*
- **Evidence:** `frontend/src/components/AnalyzeSelector.tsx` `JDInputData` has no skills field. Replaying that path moved the handwritten weak mean from 21.2 to 45.6 and pairwise accuracy from 0.976 to 0.880. On the extended set, 15 of the 16 weak pairs misbanded as medium had zero extracted job skills (e.g. `resume_backend_go` → `job_mobile_ios` scored 74.8).
- **Fix:** `resolve_required_skills()` extracts taxonomy skills from the JD when none are given. If there are still none, coverage is `None` (unknown) and `blend_final_score()` renormalizes the cross-encoder and vector weights instead of adding 25 points. The explanation omits `skillCoverage` rather than showing 100%. Job suggestions use the same code.

### 4.3 Skill synonyms and domains the map missed *(fixed, with limits)*
- **Evidence:** the taxonomy had 16 canonical skills. The Junior Java JD resolved to `['postgresql']` only. Coverage for non-tech resumes was near zero because the parser catalog is tech-only. A resume's skills came only from its parsed skills list, so "Kubernetes" written in an experience bullet didn't count.
- **Fix:** 143 canonical skills / 447 aliases (tech, finance, banking, retail, teaching, research, product and marketing), and resume text is scanned too. Over-generic aliases were tested and removed after they produced false requirements in tech JDs: `billing`/`invoicing` → accounts payable, `budget` → budgeting, `rest` → REST API, bare `security`, bare `reconciliation` (as in a Kubernetes "reconciliation loop"). `pmp` was removed because the rewrite verifier treats it as a credential.
- **Still missing:** tools like GIS, SPSS and AutoCAD. This is why R0029 (urban planning graduate with publications) scores 20.7 for Research Assistant.

### 4.4 Reranker query built from headings *(fixed)*
- **Evidence:** with no skills, `build_bounded_rerank_query` collected lines containing "skills" or "requirement", which were the headings themselves: `"Backend Engineer (Python). Required Skills Preferred Skills"`.
- **Fix:** take the body lines under requirement headings (`_extract_requirement_excerpt`).

### 4.5 Parser false positives *(fixed)*
- **Evidence:** the catalog matched case-insensitively, so "ready to **go**" meant Go and "**R**&D" meant R (also Swift, Shell, REST, Express).
- **Fix:** those names need their exact casing, and `&` ends a match.

### 4.6 Score compression on non-tech roles *(partly fixed in round 2, §8)*
- 52 of 252 Kaggle test strong pairs score 45–75. Their cross-encoder scores are high, but in the worst examples coverage is 0.14–0.44, because the JD's extracted skill list includes preferred skills and "or" alternatives ("financial statements *or* general ledger" becomes two requirements).
- **Tried and rejected:** dropping "Preferred skills" sections from extracted requirements. Kaggle tune band accuracy rose 0.783 → 0.817, but handwritten band accuracy fell 0.938 → 0.781, because the reranker query changed too. With only the coverage list changed, handwritten fell to 0.906 and tune rose to 0.801. The Kaggle labels are themselves built from required groups only, so they favour this change by construction. Not shipped.
- **Tried and rejected:** grid-fitting the blend weights and sigmoid on the tune split (Kaggle tune + extended). Kaggle test band accuracy went 0.770 → 0.873, but handwritten went 0.844 → 0.781 and pairwise slipped. Current weights (0.65 / 0.25 / 0.10, shift −3.5, temperature 2.8) and the 75/45 bands are kept.

### 4.7 Remaining misranked pairs (production, after the fixes)

Handwritten has 2 misbanded pairs and 0 inversions within a job:
- `resume_08_mobile_kotlin` → `job_07_junior_java_developer`: labeled medium, scored 42.7. The cross-encoder sees a mobile specialist for a backend role (35.5); coverage 0.60.
- `resume_03_fullstack_react` → `job_08_android_developer`: labeled weak, scored 53.8. The cross-encoder rates "web + REST + Git" against an Android JD at 60.5. This is a **seniority and platform** mismatch the cross-encoder doesn't model.

Extended has 6 medium pairs scored as weak, all "adjacent role" labels (product manager / security engineer / data engineer → Go engineer). Coverage is 0 because the resumes share no listed skill, so these are partly label questions.

### 4.8 Chunking and cross-encoder length *(checked, not a failure)*
- Resume chunks are capped at 240 tokens (`chunker.py`), and the reranker query at 180. 180 + 254 + 3 = 437 ≤ 512, so neither side is silently truncated by the cross-encoder (`test_cross_encoder_bounded_query_never_truncates_chunk`).
- Score aggregation uses the best chunk. Averaging the top 3 chunks was tried in the analysis run and was worse on the handwritten set (pairwise 0.952 vs 0.958 at the time).
- Feeding the cross-encoder the whole JD instead of title + skills was worse everywhere (handwritten pairwise 0.901, band 0.531).

### 4.9 ATS score *(reviewed)*
`intake/hazards.py` is a deterministic rule set: OCR −25, multi-column −15, tables −15, header/footer −10, unusual fonts −10, −10 per missing Experience/Education/Skills heading. There is no ML model to evaluate and no ground truth. The parsing benchmark is the only evidence, and its duplication is noted in section 2. Fixing the parser's skill false positives (4.5) also removes false skills from the ATS-facing parsed output.

## 7. Model trials (within the 2 GB worker budget)

Same harness, same splits; the only change is the model name (`RERANKER_MODEL_NAME` / `EMBEDDING_MODEL_NAME`). Memory and speed come from one bare process loading both models and then scoring 16 embeddings and 20 rerank pairs on CPU (`ru_maxrss`, Python + torch alone is 403 MB).

| Variant | Handwritten pairwise / band | Extended pairwise / band | Kaggle tune pairwise / band | Kaggle test pairwise / band | Peak RSS | Embed 16 | Rerank 20 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **Current: all-MiniLM-L6-v2 + ms-marco-MiniLM-L-6-v2** | **0.982 / 0.938** | 0.926 / **0.940** | **0.987 / 0.782** | 0.995 / 0.758 | **697 MB** | **1.70 s** | **2.54 s** |
| Reranker → ms-marco-MiniLM-L-12-v2 | 0.952 / 0.781 | 0.889 / 0.890 | 0.983 / 0.764 | 0.995 / 0.738 | 740 MB | 1.89 s | 5.24 s |
| Embedder → BAAI/bge-small-en-v1.5 | 0.982 / 0.906 | 0.928 / 0.930 | 0.987 / 0.782 | 0.995 / 0.778 | 741 MB | 4.20 s | 2.59 s |

Both alternatives fit the 2 GB worker budget (measured worker peak is about 850 MB, docs/PERFORMANCE.md). Neither is adopted:

- **L-12 reranker** is worse on every set and twice as slow. It is not a calibration artefact: its logits are on the same scale as L-6 (handwritten strong-pair mean 3.58 vs 3.30, weak −7.00 vs −7.51). Its medium pairs spread much wider (−7.89 to +3.64, vs −5.17 to +1.46) and overlap the strong ones, and recalibration can't fix that.
- **bge-small** ties on ranking, gains 2 points of band accuracy on Kaggle test, loses 3 on handwritten, and is 2.5× slower to embed. It was used without its recommended query instruction prefix. Adopting it would also mean re-embedding every stored chunk, since the vector space changes even though the 384 dimensions stay the same. Worth retrying only together with item 5 (a real labeled set).

Not tried: `bge-reranker-base` (278M parameters, about 1.1 GB in fp32). It would leave almost no headroom in the 2 GB budget on top of the worker's OCR peaks.

## 8. Round 2: sprint trials (2026-10-28)

Each change was kept only if it beat the baseline on the same harness and splits. Choices were made on the **tune** split and handwritten; the **test** split was only used for reporting. All runs used `python -m ml.eval.run` in the `project-cbp-ml` image.

### 8.1 Kept: required vs preferred skills, "or" alternatives, finance aliases

| Step (cumulative) | Handwritten pair / band | Extended pair / band | Kaggle tune band | Kaggle test pair / band |
| :--- | :---: | :---: | :---: | :---: |
| Baseline (round 1) | 0.982 / 0.938 | 0.927 / 0.940 | 0.782 | 0.995 / 0.758 |
| Preferred skills at weight 0.5 | 0.982 / 0.938 | 0.927 / 0.940 | 0.785 | 0.995 / 0.766 |
| + "X or Y" counted as one requirement | 0.982 / 0.938 | 0.927 / 0.940 | 0.814 | 0.996 / 0.786 |
| **+ finance aliases (kept)** | **0.982 / 0.938** | **0.927 / 0.940** | **0.825** | **0.996 / 0.802** |

- **Preferred weight sweep.** w = 1.0 reproduces the baseline exactly (a sanity check). w = 0.75 / 0.5 / 0.25 / 0.0 gave tune band 0.780 / 0.785 / 0.796 / 0.801 and handwritten band 0.938 / 0.938 / 0.906 / 0.906. **0.5 is the lowest weight that keeps handwritten**, set as `PREFERRED_SKILL_WEIGHT` in `ml/config.py`.
- **Where the compression came from.** On Kaggle test, misbanded strong pairs averaged CE 77 but coverage 0.38, mostly Accountant (19) and Financial Analyst (20). Two causes:
  - "excel *or* financial modeling" was scored as two requirements.
  - Resumes said "GL recs", "month-end" or "budget prep", which the map didn't know.
- **Alias source.** The aliases were mined from tune-split misbands only, then checked against the handwritten and extended JDs for collisions (none). Generic words such as "budgets" and "reporting" were left out: an earlier round removed them because they match benefits text in tech JDs.
- **Code.** `split_required_preferred`, `resolve_skill_requirements` and `extract_alternative_groups` live in `ml/pipelines/matching/skill_gap.py`. The worker and the eval runner both call them, and stored `requiredSkills`/`preferredSkills` from the JD form still take precedence. Regression tests are in `ml/tests/test_ml_failure_regressions.py`.
- **Caveat.** Kaggle labels come from required-skill groups, so they favour this change by construction (§2). Handwritten, the realistic set, stayed exactly level, which is the main evidence it isn't just fitting the labeler.

### 8.2 Rejected: rerank fewer passages (`TOP_K_CANDIDATES` 20 → 8)

The cross-encoder only ever sees one resume's chunks, and resumes are short:

| Data | Median chunks | p90 | Max | Resumes with > 8 chunks |
| :--- | :---: | :---: | :---: | :---: |
| 908 resumes in the local DB | 3 | 4 | 10 | 1 |
| Eval sets | 5.75 (handwritten mean), 1.39 (Kaggle), 1.0 (extended) | | 6 | 0 |

A cap of 8 changes the reranked set for 1 resume in 908, so it can't deliver a latency drop. The default of 20 is kept, and the eval runner now reads the same `TOP_K_CANDIDATES` setting as the worker.

### 8.3 Rejected: int8 dynamic quantization of the cross-encoder

`torch.quantization.quantize_dynamic` on the Linear layers (no new dependencies). It used 2 torch threads, same container and data:

| Set | fp32 rerank p50 / p95 | int8 rerank p50 / p95 | fp32 pair / band | int8 pair / band |
| :--- | :---: | :---: | :---: | :---: |
| Handwritten | 531 / 604 ms | 260 / 364 ms | 0.982 / 0.938 | 0.982 / 0.938 |
| Kaggle test | 97 / 222 ms | 46 / 117 ms | 0.996 / 0.802 | 0.995 / **0.778** |
| Extended | 39 / 70 ms | 18 / 28 ms | 0.927 / 0.940 | **0.921** / 0.940 |

It is 2.0–2.2× faster, but Kaggle band drops 2.4 points and extended pairwise 0.6, both beyond the 0.5-point gate. Peak RSS was 621 vs 600 MB. Not adopted. An ONNX export would need new dependencies (onnxruntime, optimum) that the image doesn't have, and the accuracy question would be the same.

### 8.4 Opt-in only: a separate OCR worker (`ml-ocr-worker`)

Parsing is serialized per process (PyMuPDF isn't thread-safe), so a 6–7 s scan blocks every text PDF queued behind it. With `OCR_QUEUE_ENABLED=true` and `docker compose --profile ocr-worker`, the parse worker hands scans to `resume-ocr-queue`. A second process, `ml-ocr-worker`, serves that queue one job at a time with a 1 GB limit and loads no transformer models.

k6 on one 4-vCPU laptop. Each scenario ran after a smoke warm-up, with queues drained between runs. Raw files are in `loadtest/results/20261028T0*`:

| Scenario | OCR inline (default) | OCR worker on |
| :--- | :---: | :---: |
| Ingestion: text PDF p50 / p95 | 1.1 s / 60.6 s | **0.6 s / 0.8 s** |
| Ingestion: OCR p50 / p95 | 5.7 s / 62.7 s | 25.6 s / 63.3 s |
| Ingestion: iterations / timeouts / dropped | 160 / 45 / 55 | **250 / 26 / 0** |
| Mixed, 2 runs each: match p50 | 23.2 s, 22.6 s | **9.3 s, 9.7 s** |
| Mixed, 2 runs each: match p95 | **31.1 s, 45.5 s** | 78.4 s, 75.0 s |
| Mixed: iterations | 972, 974 | 933, 937 |

The OCR worker removes the head-of-line blocking for text PDFs and halves median match latency. Under mixed load, though, the slowest matches get roughly twice as slow: two processes now compete for 4 vCPUs, the oversubscription noted in `docs/PERFORMANCE.md`. Since the gate was "text PDFs faster and matching no worse", it stays **off by default**. It is worth enabling on a host with more cores, and that's a sizing input for deployment. Code: `served_queues`, `process_ocr_document` and `enqueue_ocr_job` in `ml/worker.py`, plus `allow_ocr` in `parse_document`. Tests are in `ml/tests/test_worker_event_loop.py` and `ml/tests/test_parser.py`.
