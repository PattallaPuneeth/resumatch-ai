# Evaluation datasets

Versioned copies of the matching eval sets. (`test-data/` at the repo root is gitignored, so
before this folder existed nobody cloning the repo could reproduce the eval numbers.)

| Folder | Pairs | Labels | What it tests | Caveats |
| :--- | :---: | :--- | :--- | :--- |
| `handwritten/` | 32 (8 resumes × 8 jobs, partial) | strong 8 / medium 10 / weak 14, hand-written reasons | Realistic 255–296-word JDs, synonym cases (K8s ↔ container orchestration), seniority, one non-tech role | Small. Resumes and JDs are synthetic but written like real ones. |
| `kaggle_domain/` | 629 labeled (903 in source) | strong 192 / weak 437 | 301 resumes from 6 non-tech or mixed fields (accountant, teacher, banking, apparel retail, finance, research) × 16 jobs | Labels are **auto-generated by counting required skill groups** in the resume (`label_source = synthetic_description`, `review_status = auto_labeled_unverified`). This rewards keyword matching, so skill coverage looks better here than it really is. JDs are about 80 words, so they never exercise the long-JD path. The resumes appear to come from the public Kaggle "Resume Dataset" categories and contain no emails, phone numbers or profile URLs. |
| `human_hard/` | 50 (18 `test` from the kaggle test split, 32 `tune`) | strong 23 / medium 14 / weak 13, labeled by hand with a reason each | The hardest pairs from kaggle_domain and extended (near the 45/75 edges, or where the auto label and the model disagreed) | Hard by construction, so it is a stress test, not a random sample. JDs are 29–75 words. One labeler. Imported with `python -m ml.eval.import_human_labels`. |

`../ci_fixtures/` (5 pairs) is the CI gate set. `test-data/extended_dataset` (100 pairs) is
regenerated by `ml/eval/generate_dataset_100.py`. Its 4-line template resumes repeat the job
title, so it is too easy to trust on its own.

## Splits (kaggle_domain)

`labels.csv` has a `split` column assigned per resume (`tune` 377 pairs, `test` 252 pairs), so
no resume appears in both. Fit anything (weights, thresholds, aliases) on `tune` only and
report `test`:

```bash
python -m ml.eval.run --dataset ml/eval/datasets/kaggle_domain --split test --output-dir eval-output/kaggle_test
```

Rebuild from the source CSV with `python -m ml.eval.import_kaggle_dataset ml/eval/datasets/kaggle_domain`.
The 274 unlabeled source rows (`needs_manual_review`) are skipped, never guessed.

## What the next labeled dataset should look like

The next labeled set should fix the gaps found so far: short practice JDs, a single labeler,
date formats nobody tested, and too few pairs. Every requirement below comes from a problem
seen in `docs/eval/ML_FAILURE_ANALYSIS.md` section 8.

**Job descriptions**
- Real postings (job boards, company sites), full text, mostly 300–800 words. Three query
  fixes helped the 29–75-word JDs and hurt the 255–296-word ones (section 8.9), and the real
  posting pool has a median of about 480 words.
- Varied structure: headed "Required / Preferred" sections, bullet lists, single paragraphs,
  and "X or Y" alternatives.
- Mixed seniority (intern to lead) and at least 6–8 fields, tech and non-tech.

**Resumes**
- Real or realistic, with names, emails and phone numbers removed.
- Text PDF, DOCX and a few scanned PDFs; one-page and multi-page.
- Varied date formats ("Jan 2020 – Present", "(2022–25)", "(2025–)") and fresh graduates.
  Seniority parsing silently failed on formats nobody had tested (section 8.8).

**Pairs**
- 3–6 resumes per job across strong, medium and weak, so ranking metrics are meaningful.
- Hard cases on purpose: adjacent roles, right skills with the wrong seniority,
  keyword-stuffed but unqualified.
- Roughly balanced labels.
- At least 100–150 pairs for evaluation, and 500+ only if fine-tuning a model is ever planned.
- A useful minimum: about 30 real long JDs × 4 resumes each, across 6+ fields.

**Labels**
- Same definitions as `../labeling/README.md` (strong = would shortlist, medium = worth a
  second look with clear gaps, weak = would not shortlist), with a short reason for every label.
- Two labelers on at least 30% of pairs, with agreement measured, to show the ceiling a model
  can reach.
- Labeled without seeing the model's score or any auto label.

**Hygiene**
- Fix the `tune` / `test` split before any tuning, by job or resume, so no job or person
  appears in both.
- No overlap with the data used to choose aliases or settings.
- Record each item's source, date and right to use it. Keep third-party postings and real
  resumes out of git (gitignored) unless they're cleared for publishing.
- Use the same columns as `human_hard/labels.csv`
  (`resume, job, expected, reason, split, source`), so `ml.eval.run` works on it unchanged.
