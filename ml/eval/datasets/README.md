# Evaluation datasets

Versioned copies of the matching eval sets. (`test-data/` at the repo root is gitignored, so
before this folder existed nobody cloning the repo could reproduce the eval numbers.)

| Folder | Pairs | Labels | What it tests | Caveats |
| :--- | :---: | :--- | :--- | :--- |
| `handwritten/` | 32 (8 resumes × 8 jobs, partial) | strong 8 / medium 10 / weak 14, hand-written reasons | Realistic 255–296-word JDs, synonym cases (K8s ↔ container orchestration), seniority, one non-tech role | Small. Resumes and JDs are synthetic but written like real ones. |
| `kaggle_domain/` | 629 labeled (903 in source) | strong 192 / weak 437 | 301 resumes from 6 non-tech or mixed fields (accountant, teacher, banking, apparel retail, finance, research) × 16 jobs | Labels are **auto-generated by counting required skill groups** in the resume (`label_source = synthetic_description`, `review_status = auto_labeled_unverified`). This rewards keyword matching, so skill coverage looks better here than it really is. JDs are about 80 words, so they never exercise the long-JD path. The resumes appear to come from the public Kaggle "Resume Dataset" categories and contain no emails, phone numbers or profile URLs. |

`../ci_fixtures/` (5 pairs) is the CI gate set. `test-data/extended_dataset` (100 pairs) is
regenerated by `ml/eval/generate_dataset_100.py`. Its 4-line template resumes repeat the job
title, so it is too easy to trust on its own.

## Splits (kaggle_domain)

`labels.csv` has a `split` column assigned per resume (`tune` 377 pairs, `test` 252 pairs), so
no resume appears in both. Fit anything (weights, thresholds, aliases) on `tune` only and
report `test`:

```bash
python -m ml.eval.run --dataset ml/eval/datasets/kaggle_domain --split test --output-dir eval-output/kaggle_test
```

Rebuild from the source CSV with `python -m ml.eval.import_kaggle_dataset ml/eval/datasets/kaggle_domain`.
The 274 unlabeled source rows (`needs_manual_review`) are skipped, never guessed.
